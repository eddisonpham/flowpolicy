# 08. Next stage: options, tradeoffs, and what I would do first

This is a menu, not a plan of record. Every option below is sized against the current tree
(2026-10-30): one borrowed PushT checkpoint reproduced through `lerobot`'s own loop, a second
checkpoint through the same `PolicyLike`, and one open measurement — a 15-point success gap in
this repo's path on the checkpoint's own 200 seeds.

The rule from `docs/07` still holds: an option is worth taking if it either produces rows in
`results/` or makes an already-written sentence true.

## Where the stage actually is

| Claim | State | What would strengthen it |
|---|---|---|
| The stack is 20x cheaper per control step than the published setup | measured (E14) | nothing; it is a fair, same-host comparison |
| Sampler truncation to N=4 is safe | measured twice (E3 + replication) | a third block only if a reviewer asks |
| A second policy family plugs in unchanged | measured (E15, 200 paired + 200 replicated) | a third family, or a non-PushT task |
| The checkpoint reproduces on this host | measured (67.0 % vs 69.0 %, p = 0.75) | per-episode rows from the control, not aggregate |
| This repo reproduces the checkpoint | **not shown** (52.0 % vs 69.0 %, p = 0.003) | the missing DDPM@100 cell (`docs/04` §4) |
| The harness is regression-proof | partly: CPU CI covers contracts, GPU rows are one-shot | a GPU-tagged claim smoke test, or CI on a GPU runner |

## Options

### A. Finish the attribution: adapter vs sampler (recommended first)

Run this harness at the checkpoint's own DDPM@100 on the same 200 published seeds, so the
15-point gap is a two-cell decomposition instead of one number with a known cause and an
unknown split.

- **Cost:** ~2.5 h GPU, one new `just` recipe, no code.
- **Benefit:** turns the only open scientific item into a closed (or precisely located) one,
  and E0 stops being PARTIAL-by-embarrassment: if DDPM@100 lands near 67 %, the adapter is
  exonerated and the story is "truncation costs 15 points on this checkpoint", which is a
  *stronger* result than reproduction and directly supports the stack's cost argument.
- **Risk:** if it lands at 52 %, the gap is in the adapter and the next stage is a real
  debugging job (normalization, crop path, history). That is still better known than unknown.
- **Do not** raise the episode count again; 200 already resolves this question at p < 0.05.

### B. Per-episode rows from the adapter-free control

`lerobot-eval` 0.6.1 writes only aggregates (`per_task`, `per_group`, `overall`). The control
therefore compares in aggregate, while every other comparison here is paired by seed.

- **Cost:** small: either patch the writer in the isolated env, or parse its per-episode log
  and emit the same JSONL schema.
- **Benefit:** the control becomes a *paired* run, so the adapter-vs-reference comparison gets
  McNemar instead of Fisher and roughly twice the resolution for free. Also lets the control
  rows live in `results/` and be regenerated by `make_tables`.
- **Risk:** low, but patching a third-party writer is a maintenance hook — keep it inside
  `.venv-lerobot` and record the patch in `scripts/`.
- **Depends on:** nothing. Good pairing with A.

### C. Resumable, queued eval runs

`evaluate` now flushes rows to `<out>.partial` per shard and appends only on completion, so a
crash costs one shard. What is still manual is *which* runs to do and in what order.

- **Cost:** medium: a job spec (YAML or a `just` recipe list) plus a manifest of completed
  blocks, or a tiny `policybench.run` module with `--resume`.
- **Benefit:** a 3-5 h block (A plus a second family) can be started and left; interrupted
  work is not re-run; logs and rows stay attributed.
- **Risk:** the abstraction can grow past the need — this repo has ~10 eval recipes, not 200.
  Only worth it if stage 3 adds more policy families or tasks.
- **Cheaper 80 % version:** a `just block` recipe that runs `prune | evaluate` pairs in order
  with `flock`-style guards. No new module.

### D. A second task (robomimic Lift, or a second PushT checkpoint)

- **Cost:** high. G8 is NOT RUN, there is no dataset path on this host, and `docs/02` says
  robosuite/robomimic versions are a known pain point. A second PushT checkpoint is cheap by
  comparison but adds little (same task, same metric).
- **Benefit:** the only option that tests the harness against a genuinely different
  observation/action space, and the E15 claim currently rests on two PushT checkpoints.
- **Risk:** most of the work is environment archaeology, which is exactly the work this stage
  spent a day on for `lerobot` and would repeat for robosuite.
- **Verdict:** only if the goal becomes "a harness for several benchmarks" rather than "a
  deployment stack measured on one".

### E. Make the deployment path real (streaming endpoint + ROS 2 node)

- **Cost:** high: the server is synchronous HTTP today; a fixed-rate loop over it needs a
  client-side scheduler, and ROS 2 is a Docker-only path here.
- **Benefit:** converts "deployment-cost one-liner" into an end-to-end demonstration, and the
  latency story (N <= 4 for 100 ms) would be measured across a real transport rather than
  in-process.
- **Risk:** the measured number would move for reasons unrelated to the policy (socket,
  serialization), so it needs a careful protocol or it becomes a weaker E10.
- **Partial version:** measure `server.py` round-trip into the loop (the load test already
  exists) and report the added latency as a row, without ROS.

### F. Statistics hygiene as the comparison set grows

- **Cost:** low-medium.
- **Benefit:** sequential testing (alpha spending) for blocks that grow over time, and a
  multiple-comparison note once the README quotes ~8 tests. Right now the claims are few enough
  that this is honest without correction, and the README says so.
- **Risk:** over-engineering a portfolio repo; but a reviewer who knows statistics will ask
  "how many comparisons did you run?" — a one-paragraph protocol note answers it.

### G. Packaging and reach (docs site, PyPI, container)

- **Cost:** medium, mostly non-scientific.
- **Benefit:** discoverability; `pip install policybench` is a nice signal.
- **Risk:** the package is a harness with a hard GPU/simulator dependency; publishing it
  promises an API stability the project does not have. A container for the CPU half is the
  defensible slice, and it is already scaffolded in `docs/01` §5.

### H. Replace the homegrown adapter with lerobot's processor pipeline

- **Cost:** medium; depends on A's outcome.
- **Benefit:** if A shows the gap is in the adapter, adopting the library's own preprocessing
  (which the migration now produces correctly) removes a class of bugs and future-proofs the
  load path. The VQ-BeT adapter already does its own normalization, so the two would converge.
- **Risk:** loses the "measurement machinery is ours" boundary that `docs/07` rule 4 draws —
  it would need an explicit amendment, as D11 got.
- **Verdict:** contingent, and as of 2026-10-30 **drafted**: the amendment, the audit and the
  adoption design are in `docs/10`, the seam and the opt-in path are in the tree default-off, and
  the decision rule is a deterministic probe (`just processor-equiv`, 1e-6) rather than GPU hours.
  The episode arm only runs if that probe diverges, and then at a pilot-chosen 600-2,200 episodes
  (`docs/10` §5.1): 200 cannot resolve the ~4 pp the repeats left, and 4 pp itself costs 243
  episodes at 5 % discordance against 2,157 at 44 %.

## Recommended order

1. **A** (2.5 h, no code) — closes the open item one way or the other.
2. **B** (a few hours) — makes the control a paired run, which is what the next comparison
   needs anyway; also gets control rows into `results/` so tables regenerate them.
3. **F, small slice** — a short "how many tests, and what we do about multiplicity" paragraph
   in `docs/04` §1, written while the numbers are still few.
4. **C, cheap version** — only if A and B imply more multi-hour blocks.
5. **H** — only if A lands on the adapter.
6. **D / E / G** — pick at most one, and only with a new goal in mind; each changes what the
   repository is for.

What I would not do next: more episodes of what is already measured (E3's plateau, E15's
replication, VQ-BeT's rate). Every one of those is already at the resolution its question
needs, and the remaining uncertainty is in *which stage* costs the diffusion points, not in how
many samples we have.
